## Acceptance

There are two ESS pins in this repository and they move independently.

**Library pin.** `crates/agentide-xtask/Cargo.toml:21-23` takes `ess-compiler`, `ess-domain` and
`ess-realization` at one current ESS tag, with `tag` and `version = "="` agreeing on that version.

**CLI pin.** `.github/workflows/ci.yml:49` installs the `ess` binary that `validate_generated_ess`
shells out to — the gate reaches that binary through `PATH` or `AGENTIDE_ESS_BIN`, never through the
pinned library. Moving it requires, together:

- `generated/ess` regenerated with that exact tag's CLI, through the CLI and not by hand;
- `validate_generated_ess` not reading the CLI's own `.ess-output` publication ledger as an
  artifact nobody committed;
- a complete `cargo xtask gate` green against both pins at once.

`AGENTS.md` § Pins states both pins and why they differ, rather than recording a held `0.9.2` with
no reason given.

## Measured gap, 2026-09-15

`crates/agentide-xtask/Cargo.toml:21-23` pins `tag = "0.9.2", version = "=0.9.2"` three times.
ESS's latest tag is `0.24.0` (`git ls-remote --tags https://github.com/beyond10x/ess`), fifteen
minor versions later. Recorded by the beyond10x org-state review 2026-09-15-run2, lane
`10-long-tail` F7, ledger `ORG-0106`.

## Why this is release-shaped and was not done with the note

**Half of this was wrong, and measuring it is what corrected it.** The claim was an API delta across
fifteen minor versions and a different realization format. Neither is there. The library surface this
crate uses — `ess_compiler::source::SourceMap`, `ess_domain::spec::{RawSpecFile, Specification}`,
`ess_domain::system::Source`, `ess_compiler::resolve::compile_locating`, `EssIr`,
`ess_realization::{RealizationSpec, compile}` — is unchanged between `0.9.2` and `0.24.0`, and
`ess-realization/1` is still accepted beside the newer `ess-realization/2`, so the library bump took
no source edit at all.

What is release-shaped is the **CLI** half, and for one reason that was not guessed here: the
generated bytes carry a contract digest whose spelling changed, so moving the CLI tag rewrites 125
committed files and ends in this repository's own release. See the progress section for the
measurement.

## Scope

- `crates/agentide-xtask/Cargo.toml` (3 lines)
- whatever `cargo xtask generate-*` rewrites under the generated trees
- `AGENTS.md` § Pins

## Progress, 2026-09-15

Uncommitted, in a managed worktree, pending batch review. Status stays `draft`: the acceptance is a
complete `cargo xtask gate` and no such gate was run.

**Done — the library pin is at `0.24.0`.** `crates/agentide-xtask/Cargo.toml:21-23` moved to
`tag = "0.24.0", version = "=0.24.0"`; `Cargo.lock` moved 29 lines, all of them those three
packages' version and source. No source edit was needed.

Verified two ways. `cargo check -p agentide-xtask --locked` exits 0. Then the gate itself was run
with `AGENTIDE_ESS_BIN=/bin/false`, which makes `validate_generated_ess` fail on its first external
call and so stops the run before any workspace build. It reached exactly that stop, which means
`validate_contracts`, `validate_hosted_contracts`, `validate_renderer_contracts`, `validate_ess` and
`validate_realizations` all passed against `0.24.0`: `EssIr::to_canonical_json()` still equals
`generated/ess/ir.json` byte for byte, and `docs/running-modes.md` still renders byte-identically.

**Done — the drift check no longer trips on a newer CLI's ledger.** `read_tree`
(`crates/agentide-xtask/src/main.rs:1287`) filtered nothing, so `.ess-output/state.json` was read as
an artifact nobody committed. It now skips dot-prefixed entries — the root it is handed is never
filtered, only what is inside it — under two unit tests. `cargo test -p agentide-xtask --locked`
passes; with the filter removed the first test fails on exactly `.ess-output/state.json` and
`.gitignore`, which is the point of it. `cargo clippy -p agentide-xtask --all-targets --locked --
-D warnings` and `cargo fmt -p agentide-xtask -- --check` both exit 0. None of the four trees
`read_tree` reads holds a dot-prefixed artifact, so no committed byte moves.

**Not done — the CLI pin is still `0.9.2`,** and that is now the whole of this story. Measured by
regenerating `spec/agentide` with the ESS CLI `0.23.0` into a scratch tree and comparing it to
`generated/ess`: `ir.json` and four other files are byte-identical; the other 125 differ **only** in
the contract digest, `<hex>` becoming `slice-sha256/2:<hex>`; and `.ess-output/state.json` is new.
With the `read_tree` fix the ledger is no longer a difference, so nothing structural is left — what
remains is to install the CLI at the tag `.github/workflows/ci.yml:49` will name, regenerate
`generated/ess` with it, and gate. That needs a build of the ESS CLI, which did not fit the disk
budget of the pass that did the library half.

**Not done — a complete `cargo xtask gate`.** It runs `cargo check`, `cargo test` and `cargo clippy`
over the whole workspace, `npm ci` and the browser build; the disk budget barred all of it. Every
claim above is package-scoped or comes from the stubbed gate run, and this story stays open until a
full gate is green with both pins current.
